# Fork divergence from upstream

This fork tracks `upstream/main` (github.com/reactive-resume/reactive-resume; formerly amruthpillai/reactive-resume, which GitHub redirects). Upstream is a multi-user, marketing-forward SaaS product; this fork is a single-owner personal tool.

Read this file before syncing or cherry-picking from upstream, and before editing any file it names. `AGENTS.md` keeps only a summary.

An agent doing an upstream sync has a structural blind spot here: a 3-way merge or a cherry-pick cannot know that a file upstream reintroduces was deleted on purpose. **Treat every item below as intentional unless the owner says otherwise, re-verify it after every sync** rather than trusting a clean apply, and ask the owner before reintroducing anything in "Removed entirely", even if upstream's version looks improved.

## Sync policy

The fork was fully merged up to upstream `11571ae` (v6.0.0 + fixes). **From then on, sync by cherry-picking upstream commits (`git cherry-pick -x`), not by merging `upstream/main`:** upstream's `ba4bec2b` ("feat(career): add career and application workspaces") adds a Career area that this fork does not adopt and rewires Applications, interview scheduling, the Assistant backend, account export and the icon system around it, so a full merge would pull all of that in.

- Pick fixes and resume-builder improvements. Skip commits that only serve Career, Applications or cover-letter documents, and drop their hunks from mixed commits.
- **Do not copy upstream migration folders.** Upstream's later migrations chain through its Career snapshot (`20261007205051_career_platform`), which this fork does not have. Apply the commit's `packages/db/src/schema/*` change, then run `pnpm db:generate` and review the SQL (see "Environment and database" in `AGENTS.md`).
- **Sync on `claude/dev`.** Upstream picks land on the long-lived `claude/dev` branch, which merges `main` in before each sync and reaches `main` through a pull request. Pushes to `claude/dev` run the same workflows as `main` (Code Quality, E2E Tests, Build Docker Image); the image build there only tags `sha-<commit>`, never `nightly` or a release.
- Record every decision in the ledger below. `git log --grep "cherry picked from"` also lists taken commits through the `-x` trailer, but skipped commits leave no trace in git, so the ledger is the only record of them.

## Behavior kept intentionally different

- **Single-owner auth** (`packages/auth/src/single-owner.ts`) — no open multi-user signup, no teams/orgs/roles.
- **No `genericOAuthClient` in the web auth client.** better-auth 1.7.2 stopped exporting it; the server keeps the `genericOAuth` plugin (`packages/auth/src/config.ts`), and nothing in the web app calls a generic-OAuth client method, so the client plugin list simply omits it.
- **`mainEntryBold` per-item toggle, default unbold.** Company, school, project name, certification title, skill name, language and profile network render **unbold by default**, with an explicit "Bold" checkbox per entry to opt in. Upstream instead treats these as unconditional "Bold hosts" (always bold, no toggle) and only exempts award titles. Every export path (PDF, DOCX and ODT) must read `item.mainEntryBold ?? false` for exactly these seven fields, and leave headings without the toggle (publication title, reference/interest name, volunteer organization) unconditionally bold. Touches: `packages/schema/src/resume/data.ts` (field), `packages/pdf/src/templates/shared/sections.tsx` (`MainEntryText`/`ItemTitle` primitives; projects and certifications pass `toggleBold` to the shared `DatedItemSection`, publications don't), `packages/docx/src/section-renderers.ts` (`titleAndSubtitle` bold argument, the skill run, and `nameLine`'s `bold` argument for languages and profiles), `packages/odt/src/sections.ts` (`mainEntryBold` helper, pinned in `odt.test.ts`), and the v6 Write panel's `MainEntryBold` checkbox in `apps/web/src/features/resume/editor/write/entries.tsx` (v6 removed the old item dialogs). PDF and DOCX must agree; `packages/docx/src/section-renderers.test.ts` pins the defaults and the opt-in, and `packages/pdf/src/templates/shared/sections.test.ts` pins the PDF wiring.
- **The toggle renders a real bold weight, not the `bold` style slot.** Upstream's `bold` slot resolves to `typography.body.fontWeights.at(-1)`, which is 500 by default and collapses onto the body weight when the author selects a single weight — so the checkbox produced little or no visible change while DOCX wrote true bold. The toggle instead uses the `mainEntryBold` style slot (`resolveMainEntryBoldWeight` in `packages/pdf/src/templates/shared/base-template-styles.ts`): `max(700, heaviest authored body weight)`. `registerFonts` already registers 700 for the body family, so the face always exists. `packages/pdf/src/semantic/base-styles.ts` mirrors this per item (`MAIN_ENTRY_BOLD_FIELDS`) so the Semantic CSS declared base matches what renders and `revert` restores the right weight. Pinned by `packages/pdf/src/templates/shared/main-entry-bold.test.tsx` in both legacy and semantic modes and by the Onyx cases in `packages/pdf/src/semantic/base-reset-fidelity.test.tsx`.
- **Resume JSON editor is restored** (`apps/web/src/routes/builder/$resumeId/-components/edit-json-dialog.tsx`, opened from **Edit JSON…** in the editor's document menu, `-components/document-menu.tsx`, and mounted per opening so it always starts from the current resume). Upstream removed direct JSON editing in favor of guided forms plus the Semantic CSS stylesheet editor; this fork keeps both the guided forms _and_ a raw JSON editing escape hatch.
- **Root public resume (`ROOT_RESUME_ID`) adopted, but behind the fork's dashboard redirect.** Upstream's feature — serve one public resume at `/` — fits a single-owner instance, so `packages/api/src/features/resume/root.ts`, the `getFallbackResponseHeaders` branch and the noindex shell in `apps/server/src/static/web.ts`, and the loader/head/component branches in `apps/web/src/routes/_home/index.tsx` are all kept. The fork's `beforeLoad` redirect to `/dashboard` (v6's Documents library) stays **ahead** of the loader, so a signed-in owner lands in the dashboard and only visitors see the root resume. A create/import action picked on the first-visit hero survives sign-in (`apps/web/src/features/resume/start-intent.ts`) and opens v6's **New** dialog once from `apps/web/src/routes/dashboard/index.tsx`. `apps/server/src/static/web.ts` keeps `escapeAttribute` solely for that shell's canonical link; the marketing/ATS/public-resume markup injections around it stay removed.
- **Legacy→Semantic CSS converter carve-out** (`packages/pdf/src/semantic/legacy-converter.ts`, `scizorBoldColorSelector`/`TOGGLE_BOLD_SECTION_TYPES`): the converter does not apply Scizor's "Bold-after-text" color restoration to experience/education/projects/certifications/skills headings, because in this fork those are `mainEntryBold`-toggle-driven rather than unconditional Bold hosts. If upstream reworks this converter again, re-check that this carve-out still exists — a clean text-level merge can silently drop it.

- **UI icons are Phosphor, as upstream.** The fork kept Material Symbols until the 2026-10-27 sync, when `ed3abe35` was taken; the Material font, `packages/ui/src/icons/names.ts` and `pnpm icons:build` are gone. New icons go in the `icons` registry in `packages/ui/src/components/icon.tsx`. Upstream code arriving with Material names (none should now) would fail typecheck.
- **AUTH_SECRET length check not adopted** (pending above): production only refuses the `.env.example` placeholder secrets.
- **Account export is resumes-only.** "Export everything" (`authService.exportData`, `buildAccountZip` in `packages/utils/src/account-zip.ts`) writes the account, resumes, resume version history and the uploads those resumes reference, with `upload-manifest.json`; upstream also exports applications, Career, letters and feedback. ## Added beyond upstream

- **Linked parent/child resumes with selective parent-update sync.** "Create child resume" is intentionally different from an ordinary duplicate: the child records `parentId`, the last reviewed `parentRevision`, and a `parentData` snapshot (`packages/db/src/schema/resume.ts`). When the parent changes, the resume service computes JSON Patch operations from that snapshot to the current parent, rebases item paths onto the independently edited child, reports human-readable diffs and overlapping child-edit conflicts, and can apply only the caller-selected operation paths, force selected conflicts, or dismiss the current parent updates without changing child content (`packages/resume/src/patch.ts`, `packages/api/src/features/resume/{service,crud}.ts`, `packages/api/src/dto/resume.ts`). Preserve the creation flow (`ResumeDialog` with `mode="derive"` in `apps/web/src/dialogs/resume/index.tsx`, dialog type `resume.derive`, rendered from `apps/web/src/dialogs/renderers.tsx`); do not reduce this to plain duplication or all-or-nothing parent replacement. The web UI exposes **Create child resume** from both the Documents library card menu (`apps/web/src/features/documents/document-actions.tsx`) and the editor's document menu, and the review surface is a badge button in the editor bar (`-components/editor-bar.tsx`, the first child of upstream's `EditorBarFrame`, → `-components/parent-updates.tsx`) — it consumes `getSyncStatus`, `applyParentUpdates`, and `dismissParentUpdates`, renders each pending operation as a selectable row via the pure formatters in `apps/web/src/features/resume/sync/diff.ts`, and only sends `force: true` for conflicting rows the author explicitly confirms. Before applying it saves pending edits (`savePendingChanges`) and then loads the returned resume with `replaceResumeFromServer`, so a stale autosave can never write over the applied updates. Every content write bumps `resume.revision`; resume responses expose `revision`/`parentId`/`parentRevision` but never `parentData`, and account exports omit the lineage.
- **`lmstudio` AI provider** (LM Studio), on top of upstream's provider list — see `AI_PROVIDERS` in `packages/ai/src/types.ts`, its base URL and model suggestion in `packages/ai/src/defaults.ts` (where Ollama also keeps its local endpoint), `getModel` in `packages/api/src/features/ai/service.ts`, and the v6 settings UI (`apps/web/src/features/settings/ai/{catalog,providers}.tsx`). Ollama defaults to the local endpoint; Ollama, LM Studio and OpenAI-compatible providers accept an empty API key (`isApiKeyOptional`, `packages/api/src/features/ai-providers/inputs.ts`), local providers may use private/http base URLs and skip the public-only `aiTransport` (`url-policy.ts`), and malformed local-model JSON maps to a 400 (`rethrowAiError` in `packages/api/src/features/ai/router.ts`).
